Why Edit scrolls the page back to the top

The saved entries live in a table at the bottom of a long page. The form that edits them is at the top. When someone clicks Edit on a row, the app fills in the form, and one line then brings the form into view:

app.js:173window.scrollTo({ top: 0, behavior: 'smooth' });

Without it, the edit happens where the user cannot see it. Play the sequence below, then switch the scroll behavior to compare.

    What the smooth scroll gives the user

    They see the result of their click

    Filling the form is the only response to Edit. If the form is off screen, the click appears to do nothing. Scrolling puts the response in front of them.

    They don't have to go find the form

    The next thing they need is the first field. The app takes them there, which saves a manual scroll on every edit, and a long one on a phone.

    They keep their bearings

    An animated scroll shows the page moving upward. The user can tell this is the same page and that the table is still below. A jump gives no such clue.

    The change of mode is noticeable

    The form now updates an existing entry, and its button reads Update Entry. Arriving at the form with the old values already in it makes that hard to miss.

    Reading the call

    top: 0
    A vertical position in pixels, measured from the top of the document. Zero is the very top of the page, above the heading, so the form's first fields come into view.
    behavior: 'smooth'
    Asks the browser to animate the scroll. The other values are 'instant' (jump) and 'auto' (follow the page's CSS scroll-behavior, which is a jump by default).
    It does not wait
    scrollTo starts the animation and returns straight away. The console.log on line 174 runs while the page is still moving.
    Order matters
    The form is populated on line 172, before the scroll on line 173. By the time the form slides into view it already holds the entry's values.
    What it leaves out
    It moves the view, not keyboard focus, so a keyboard or screen reader user is still on the Edit button. It also aims at pixel 0 instead of at the form. carbonFootprintForm.scrollIntoView({ behavior: 'smooth' }) followed by a focus() on the first input would cover both.
